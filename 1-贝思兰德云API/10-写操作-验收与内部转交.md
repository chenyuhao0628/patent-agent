## 3.7 统一验收：保存完成但不要混淆提交层级

### 路线专用只读验收

**申请原文卡片** —— 验收条件是五个拆分项全部存在：

```text
100001  权利要求书
100002  说明书
100003  说明书附图
100004  说明书摘要
100005  摘要附图
另有     IsMixFile=true 的原始混合文件
```

**补正表** —— 验收 `CorrectionReasonType`、`IsAddEntrust`、通知书三字段（仅原因 2）以及每条 `CorrectionContentList`。

**意见陈述书** —— 验收 `Data.File`、`Data.OpinionStatement`、Word 文件编号和通知书三字段。**100012 不能用普通 `GetFormFile` 代替专用接口验收。**

**提出申请请求书** —— 验收 `FormCode` 对应的请求书对象和页面必填字段。

### "提交"与"正式递交"是两件事

递交分三个层级，本节只覆盖前两个：

1. **保存表单**：只保存文件或业务字段。
2. **内部流程提交**：把当前递交实例送到下一个内部流程节点，调用 `SubmitHandFlow`；这一步可以把案件交给下一办理人，由其继续后续工作。

完成上传或内部转交都**不等于**已经正式递交。本节的终点是把案件提交给下一办理人；打包、官方校验、官方发送在 [11-写操作-官方递交流程.md](./11-写操作-官方递交流程.md) 与 [CPC 分册](../3-CPC电子申请客户端/5-提交流程完整接口.md) 里，由接收人按所选路线执行。

## 3.8 内部流程提交（会改变流程状态）

### 读取下一节点和办理人

```bash
curl -sS -k --get "$API/CaseInfo/GetHandNextFlowList" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseReviewDraftId=$CASE_HAND_ID"

curl -sS -k --get "$API/CaseInfo/GetHandNextFlowUserByStepId" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode 'caseHandStepId=<从上一响应选择的节点 ID>'
```

### 直接转交给下一办理人

这条路线**只改变内部办理人，不代表已经向官方递交**，因此不调用 `VerifyBeforeCaseHand`、`GetPackInfo`、`StartPack` 或 `StartCaseHandSend`。

```json
{
  "CaseHandId": "<CaseHandId>",
  "IsOutSideSend": false,
  "CaseHandStepId": "<下一节点 ID>",
  "NextFlowUserid": "<下一办理人 ID>",
  "CCUserIdList": [],
  "Remark": "<备注，可为空>"
}
```

```bash
curl -sS -k -X POST "$API/CaseInfo/SubmitHandFlow" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  -H 'Content-Type: application/json' \
  -d "$SUBMIT_BODY"
```

**仅在以下条件同时满足时使用**：目标节点和办理人已经从接口返回，且操作者明确要求由该办理人继续后续工作。

提交后**必须重新读取 `GetHandInfo`**（见 2.5），确认 `CurrentFlowInfo.FlowUserName` 和 `FlowNodeName` 已切换；**不要仅凭 HTTP 200 判断成功**。

## 3.9 官方递交不属于本流程

当前命令行流程**明确禁止**调用：

```text
GET  /CaseInfo/GetPackInfo
GET  /CaseInfo/StartPack
POST /CaseInfo/VerifyBeforeCaseHand
GET  /CaseInfo/StartCaseHandSend
GET  /CaseInfo/GetCaseHandSendInfo
GET  /CaseInfo/CancelCaseHandSend
```

这些接口属于接收人后续的官方递交工作，不是"提交给下一办理人"的一部分。

完整的官方递交链路（打包 → 校验 → 递交 → 状态机 → 官文回传）见 [11-写操作-官方递交流程.md](./11-写操作-官方递交流程.md)。

## 3.10 接口适用范围

各业务对象都有与之匹配的专用接口，**按下表选用**：

| 业务对象 | 使用接口 | 对应章节 |
| --- | --- | --- |
| 申请原文卡片（五书 + 原始混合文件） | `UploadExistFileFormInstructionsAndImage` → `ModifyFormInstructionsAndImage` | 3.4 |
| 补正书 | `InsertFormCorrection` / `UpdateFormCorrection` | 3.5 |
| 意见陈述书 | `InsertFormOpinionStatement` / `UpdateFormOpinionStatement` | 3.6 |
| 请求书 | `InsertFromPatentRequestInfo` / `UpdateFormPatentRequestInfo` | 3.4 |

### 与通用文件接口的区别

以下通用接口不感知各表单的结构与校验规则，适用于无专用接口的普通附件场景：

```text
POST /CaseInfo/UploadFormFile
POST /CaseInfo/InsertFormFile
POST /CaseInfo/UpdateFormFile
GET  /CaseInfo/GetFormMultiFile
GET  /CaseInfo/GetHandFileListWo
```

上表四类业务对象**不使用**这些接口保存，否则表单结构、必填校验和后续流转都会出问题。

### 申请原文卡片的历史接口

```text
POST /CaseInfo/UploadHandMixFileWo
POST /CaseInfo/SaveHandCutMixFileWo
```

这套旧组件只产生四个拆分文件，缺少 `摘要附图` 与 `IsMixFile=true` 的原始混合文件。当前卡片请使用 3.4 的路线。
