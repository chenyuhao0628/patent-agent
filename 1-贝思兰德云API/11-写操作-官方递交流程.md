# 写操作 · 官方递交流程

> 总目录：[接入文档](../README.md) ｜ 分册：[贝思兰德云 API](./README.md)
> 上一节：[10-写操作-验收与内部转交.md](./10-写操作-验收与内部转交.md) ｜ 下一节：[99-归档-无权限与无数据.md](./99-归档-无权限与无数据.md)

本节说明**从「文件制作完成」到「官方收到回执」的完整递交链路**。

> ⚠️ **本节全部接口都会向官方递交真实案件，不可撤销。**
>
> 选择路线：
> - 走**贝思兰德服务端代发** → 用本节的接口，需先在贝思兰德后台开通递交权限并绑定官方账号（绑定见 [国家知识产权局网关分册](../2-国家知识产权局网关/3-与专利流程的关系.md)）；

## 一、两条状态机

递交过程由两个状态码驱动：**先打包，后递交**。

### 递交状态 `SendStatus`

取自状态字典接口（**权威，可直接查**）：

```bash
curl -sS -k --get "$API/SystemTypeSetting/GetCaseHandSendStatusViewTypeList" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN'
```

返回：

```json
[
  {"label": "待递交",     "value": 0},
  {"label": "准备递交中",  "value": 1},
  {"label": "递交成功",   "value": 2},
  {"label": "递交失败",   "value": 3},
  {"label": "已收到回执",  "value": 6},
  {"label": "递交中",     "value": 100}
]
```

| 值 | 名称 |
| --- | --- |
| `0` | 待递交（编辑） |
| `1` | 准备递交中 |
| `100` | 递交中 |
| `2` | 递交成功 |
| `3` | 递交失败 |
| `6` | 已收到回执 |

**没有 `4`、`5`**——字典里直接跳过。

前端轮询用 `[1, 100]` 判断「仍在进行中」，即 `1` 与 `100` 需要继续轮询。

### 打包状态 `PackageStatus`

来自**五书打包**接口：

```bash
curl -sS -k --get "$API/CaseInfo/FiveFormsGetPackInfo" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandId=$CASE_HAND_ID"
```

返回 `{PackageStatus, ErrorMessage}`。

| 值 | 含义 | 界面文案 |
| --- | --- | --- |
| `0` | 待打包 | 准备打包中 |
| `100` | 打包中 | 打包中 |
| `1` | 打包成功 | — |
| `2` | 打包失败 | — |

`null` 与 `3` 都按 `0`（待打包）处理。

打包成功后前端会去取递交实例文件列表（见 2.14 的 `GetCaseHandFileList`）。轮询用 `[1, 100]` 判断进行中。

## 二、递交接口与权限

递交分**单案**与**批量**两条路，走不同的接口，权限也分开。

### 2.1 单案递交

```text
① 校验    GET /CaseInfo/VerifyBeforeCaseHand        递交前校验
② 递交    GET /CaseInfo/StartCaseHandSend?caseHandId=   递交官方
③ 轮询    GET /CaseInfo/GetCaseHandSendInfo?caseHandId= 查递交状态
④ 取消    GET /CaseInfo/CancelCaseHandSend?caseHandId=  取消递交
```

状态也可从案件列表行直接看（见 [4-只读-流程链路与卡点.md](./4-只读-流程链路与卡点.md)）：

| 字段 | 含义 |
| --- | --- |
| `CaseHandSendStatusName` | 递交状态名称 |
| `CaseHandHasPack` | 是否已打包 |
| `CaseHandHasImportClient` | 是否已导入客户端 |
| `CaseProcNameInfo.CaseProcName` | 流程节点名 |
| `GetHandInfo.IsPackageSendSuccess` | **是否已递交官方** |

### 2.2 批量递交

```text
① 选流程   POST /CaseHandBatchSend/GetStartChooseCaseProcList
② 打包     POST /CaseHandBatchSend/StartPack      body: {CaseHandIdGroup:[...]}
③ 查打包   POST /CaseHandBatchSend/GetPackStatus   body: {CaseHandIdGroup:[...]}
④ 递交官方  POST /CaseHandBatchSend/Start          body: {CaseHandIdGroup:[...]}
⑤ 递交完成  （由递交人操作）
⑥ 移回待递交 POST /CaseHandBatchSend/...
⑦ 重打包   POST /CaseHandBatchSend/ResetPack
⑧ 列表     POST /CaseHandBatchSend/GetBatchList
           body: {"ListType":1|2|3, "SendStatus":null, "pageIndex":1, "pageSize":10}
           ListType: 1=待递交  2=待递交官方  3=已完成
⑨ 计数     POST /CaseHandBatchSend/GetBatchListCount
```

#### 实测权限：批量递交整套未开通

| 接口 | 权限 |
| --- | --- |
| `GetCaseHandSendStatusViewTypeList` | ✅ |
| `VerifyBeforeCaseHandBatchSend` | ✅ |
| `VerifyBeforeCaseHandBatchSend`（`/CaseInfo/` 下） | ✅ |
| `GetAllStartCaseHandSendInfo` | ✅（返回 `{DataGroup: []}`） |
| `GetApplicantCnListDropdown` | ✅（6 条） |
| `GetBatchList` | ❌ 无权限 |
| `GetBatchListCount` | ❌ 无权限 |
| `GetPackStatus` | ❌ 无权限 |
| `GetStartChooseCaseProcList` | ❌ 无权限 |
| `VerifyBeforeImportClient` | ❌ 无权限 |

**按需开通，不要重试。**

### 2.4 递交前校验

不改变任何状态，可以放心调用，用来判断**哪些案子当前能递交、哪些不能、原因是什么**。

```bash
curl -sS -k -X POST "$API/CaseInfo/VerifyBeforeCaseHandBatchSend" \
  -H "Authorization: $TOKEN" -H 'Origin: $ORIGIN' \
  -H 'Language: zh-CN' -H 'Content-Type: application/json' \
  -d '{"CaseHandIdGroup":["81c296c9-c9a0-4b15-add4-711ceeac7bd2"]}'
```

返回：

```json
{
  "Status": "VerifyHandInfoFail",
  "AllHandInfoGroup": [],
  "VerifyFailHandInfoGroup": [{
    "CaseHandId": "81c296c9-...",
    "CaseProcId": "1a3f1cd9-...",
    "CaseNo": "202606292-0634",
    "CaseName": "一种带有气体净化组件的汽车零件喷漆设备",
    "CaseProcName": "答复审查意见(一)",
    "HasImportClinet": false,
    "Status": "NoPermit",
    "UserCode": null
  }],
  "UserCode": null,
  "UserType": 0
}
```

| 字段 | 含义 |
| --- | --- |
| `Status` | 整体校验结果，`VerifyHandInfoFail` = 有案件未通过 |
| `AllHandInfoGroup` | 通过校验的案件 |
| `VerifyFailHandInfoGroup` | 未通过的案件及原因 |
| `HasImportClinet` | 是否已导入本机 CPC 客户端 |
| `Status`（组内） | 失败原因，`NoPermit` = **当前账号无递交权限** |

## 三、单案递交：三个步骤

```text
① 校验  VerifyBeforeCaseHand
      │ 通过
      ▼
② 递交  StartCaseHandSend
      │
      ▼
③ 轮询  GetCaseHandSendInfo
```

### ① 校验

递交前必须先打包并校验。校验分两部分：**打包状态检查** + **表单内容检查**。

```bash
# 查打包状态
curl -sS -k --get "$API/CaseInfo/GetPackInfo" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandId=$CASE_HAND_ID"

# 递交前校验（请求体为 buildVerifyParam 构造的完整校验参数）
curl -sS -k -X POST "$API/CaseInfo/VerifyBeforeCaseHand" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  -H 'Content-Type: application/json' \
  -d "$VERIFY_BODY"
```

校验调用携带的开关（来自前端 `handVerify`）：

| 参数 | 含义 |
| --- | --- |
| `isSend` | 本次校验用于「递交」动作 |
| `isBeforeSend` | 递交前校验 |
| `useVerify` | 启用内容校验 |
| `useTwiceVerify` | 双重校验 |
| `verifyType` | `VerifyData` |

**校验返回 `IsSuccess=false` 时**，响应中带 `PreHandResult`，其中包含需要人工确认的问题项：

| 字段 | 提示内容 |
| --- | --- |
| `NoEntrustNumberApplicantNameGroup` | 申请人【xxx】缺少专利代理委托书 |
| `CaseEntrustIsNotFeeReduceWhenAllApplicantFeeReduce` | 费减相关 |
| `NotExsitPriorDASFormWhenCaseEntrustIsApplyDAS` | DAS 优先权相关 |
| `NotCheckHasSequenceListingWhenExsit100133Form` | 已勾选 ST.26 序列表但请求书未勾选 |
| `VerifyResultList` | 逐条校验结果，`Type` 为 `Custom` 或 `SubstantiveExamination*` |

### ② 递交

```bash
curl -sS -k --get "$API/CaseInfo/StartCaseHandSend" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandId=$CASE_HAND_ID" \
  --data-urlencode "tenantCpcUserInfoId=$TENANT_CPC_USER_INFO_ID" \
  --data-urlencode "isCheckDeliver=true"
```

参数含**官方递交账号 ID**（`tenantCpcUserInfoId`），即扫码绑定后保存的那个。

返回 `Status` 字段，取值包括：

| `Status` | 含义 | 处理 |
| --- | --- | --- |
| 成功态 | 已受理 | 进入轮询 |
| `NeedConfirm` | 需要人工确认 | 前端弹确认，确认后重发 |
| `SendAppIsBusy` | **客户端忙** | 等待后重试 |

### ③ 轮询状态

```bash
curl -sS -k --get "$API/CaseInfo/GetCaseHandSendInfo" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandId=$CASE_HAND_ID"
```

返回：

```json
{
  "SendStatus": 100,
  "ErrorMessage": null,
  "NotifyInfo": {
    "NoticeType": 1,
    "RemainSeconds": 60,
    "Data": "<二维码内容>"
  }
}
```

- **`SendStatus`** —— 按第一节的枚举判断进度
- **`NotifyInfo`** —— 非空时表示**官方要求二次认证**，前端需展示二维码让用户扫码（`NoticeType` 为 `1` 或 `3`）。二维码内容由**服务端下发**，前端只渲染与倒计时
- **`ErrorMessage`** —— 失败时的具体原因

> 轮询在客户端进行，间隔 **500 毫秒**。

### 取消递交

```bash
curl -sS -k --get "$API/CaseInfo/CancelCaseHandSend" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandId=$CASE_HAND_ID"
```

仅在 `SendStatus = 1`（准备递交中）且尚未打包成功时可用。

## 四、批量递交的执行细节

接口与参数见 [第二节 2.2](#22-批量递交)。本节补充**执行特征**，这些会影响轮询策略与失败处理。

### 批量递交的执行特征

**串行逐案，不是并发**。前端逻辑：

```text
for 每个案件:
    ① StartCaseHandSend(caseHandId, tenantCpcUserInfoId, ...)
    ② 若成功:
         DeliverStatusName = "准备递交中"
         轮询 GetCaseHandSendInfo 直至状态稳定（间隔 500ms）
    ③ 若 Status = "SendAppIsBusy":
         重启客户端 → 等待恢复 → 重试本案
    ④ 若其他失败:
         该案标记失败，继续下一个
```

**关键行为**：

| 行为 | 说明 |
| --- | --- |
| 串行 | 一次只递交一个案件，避免客户端并发冲突 |
| 遇到 `SendAppIsBusy` | 自动重启 CPC 客户端后重试，不算失败 |
| 中途已有成功 | 中断后重试时跳过已成功的案件 |
| 完成后 | 轮询直到 `成功 + 失败 = 总数`，再关闭进度弹窗 |

### 其他批量接口

```text
POST /CaseHandBatchSend/GetBatchList            批次列表
POST /CaseHandBatchSend/GetBatchListCount       批次数量
POST /CaseHandBatchSend/ResetPack               重置打包
POST /CaseHandBatchSend/GetStartChooseCaseProcList   可选案件流程
POST /CaseHandBatchSend/VerifyBeforeImportClient     导入客户端前校验
POST /CaseHandBatchSend/DeleteCaseHand          移除批次内案件
GET  /CaseHandBatchSend/GetAllStartCaseHandSendInfo  全部递交状态
```

## 五、案卷包导出（交给 CPC 客户端的中间产物）

**这是「贝思兰德 → 本机 CPC 客户端」的衔接环节**：贝思兰德把案件打成官方格式的案卷包，下载后交给客户端导入提交。

### 5.1 完整链路

```text
① 打包      GET  /CaseInfo/StartPack?caseHandId=&isForce=&hasConfirm=      改变状态
② 查打包    GET  /CaseInfo/GetPackInfo?caseHandId=                         只读
③ 下载      POST /CaseInfo/BatchDownloadCaseHandFile                       只读
             body: {"CaseHandIdGroup": ["<caseHandId>", ...]}
             ← {Result, OssFileUrl, ErrorFile}
④ 标记已下载 GET  /CaseInfo/MarkHasDownloadCaseHandPack                     ❌ 无权限
⑤ 导入客户端
⑥ 标记已导入 GET  /CaseInfo/MarkHasImportCaseHandPack?caseHandId=            ⚠️ 参数待确认
```

### 5.2 打包

```bash
curl -sS -k --get "$API/CaseInfo/StartPack" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandId=$CASE_HAND_ID" \
  --data-urlencode "isForce=false" \
  --data-urlencode "hasConfirm=false"
```

| 参数 | 说明 |
| --- | --- |
| `caseHandId` | **必需**，递交实例 ID |
| `isForce` | 是否强制重打包 |
| `hasConfirm` | 是否已确认（表单变更时重打包需要） |

相关：

```text
GET /CaseInfo/CancelPack?caseHandId=              取消打包
GET /CaseInfo/ResetPack?caseHandId=&isForce=      重置打包
```

### 5.3 查打包状态

```bash
curl -sS -k --get "$API/CaseInfo/GetPackInfo" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandId=$CASE_HAND_ID"
```

未打包时返回 `Data = null`。

**五书单独打包**（`SystemCompany/CanSeparatePackFiveForms` 返回 `true` 时可用）：

```text
GET /CaseInfo/FiveFormsStartPack?caseHandId=      开始五书打包
GET /CaseInfo/FiveFormsGetPackInfo?caseHandId=    查五书打包状态（返回 PackageStatus）
GET /CaseInfo/FiveFormsResetPack?caseHandId=      重置
```

### 5.4 下载案卷包

```bash
curl -sS -k -X POST "$API/CaseInfo/BatchDownloadCaseHandFile" \
  -H "Authorization: $TOKEN" -H 'Origin: $ORIGIN' \
  -H 'Language: zh-CN' -H 'Content-Type: application/json' \
  -d '{"CaseHandIdGroup":["'"$CASE_HAND_ID"'"]}'
```

返回：

```json
{
  "Result": "NoFile",
  "OssFileUrl": null,
  "ErrorFile": null
}
```

| 字段 | 含义 |
| --- | --- |
| `Result` | `NoFile` = 当前无可下载文件；有文件时返回成功标识 |
| **`OssFileUrl`** | **案卷包的下载地址**（OSS 签名 URL，有效期有限，现取现用） |
| `ErrorFile` | 出错的文件信息 |

**`OssFileUrl` 就是案卷包本体**——下载后即为官方格式 zip，可直接交给 CPC 客户端导入，见 [CPC 分册 5-提交流程完整接口.md](../3-CPC电子申请客户端/5-提交流程完整接口.md) 第二节。

同类接口：

```text
POST /CaseInfo/BatchDownloadCaseHandFile        递交实例文件（案卷包）
GET  /CaseInfo/BatchDownloadCaseHandCommonFile  常用文件   {caseHandId}
GET  /CaseInfo/BatchDownloadCaseHandUSFile      美国案件文件 {caseHandId}
```

三个都返回 `{Result, OssFileUrl, ...}` 同构结构。

### 5.5 标记已下载 / 已导入

这两个接口**只把界面上的两个 Yes/No 标记置位**，不参与实际递交流程。

#### 参数

```text
GET /CaseInfo/MarkHasDownloadCaseHandPack?caseHandId=<caseHandId>
GET /CaseInfo/MarkHasImportCaseHandPack?caseHandId=<caseHandId>
```

两个都是 `{caseHandId}`。已通过与它们同形状的只读接口交叉验证：

```text
GetCaseHandCpcUserCode?caseHandId=        ✅
GetCaseHandNextStepInfo?caseHandId=       ✅
GetPackInfo?caseHandId=                   ✅
GetCaseHandSendInfo?caseHandId=           ✅
```

#### 权限与前置条件

| 接口 | 结果 | 说明 |
| --- | --- | --- |
| `MarkHasDownloadCaseHandPack` | ❌ **无访问权限** | 菜单：`批量处理管理 - 批量递交 - 批量递交(batchdeliver) - 标记打包文件已被用户下载` |
| `MarkHasImportCaseHandPack` | ⚠️ **有权限，但报 `系统错误: e`** | **不是参数问题**——该案未打包、未下载、未导入，没有可标记的记录 |

> **`系统错误: e` 与「无访问权限」的区别**：前者说明权限检查已通过，失败在业务逻辑；后者才是权限缺失。
> 判断一个接口能不能用，看这两个返回的差异，不要一律当成"参数不对"。

#### 它们置位的是哪两个字段

递交管理列表里的三列，前两列就是这两个接口控制的：

| 列字段 | 含义 | 由谁置位 |
| --- | --- | --- |
| `CaseHandSendStatusName` | 递交状态 | 递交流程自动维护 |
| **`CaseHandHasPack`** | **是否已打包** | `MarkHasDownloadCaseHandPack` |
| **`CaseHandHasImportClient`** | **是否已导入客户端** | `MarkHasImportCaseHandPack` |

列表的筛选器字段：`CaseHandSendStatus` / `HasPack` / `CaseHandHasImportClient`。

#### 调用时机（从前端逻辑还原）

```text
批量下载（batchDownload）
  for 每个选中案件:
      await downloadFile(案件.PackageFileNo)          下载案卷包
      MarkHasDownloadCaseHandPack(案件.CaseHandId)    ← 标记已下载

导入客户端（importClientHandler）
  ① 下载案卷包文件（按 PackageFileNo）
  ② 构造 FormData: file=<guid>.zip, reqType=cn
  ③ 按 IsWoCountry 分流导入到本机 CPC 客户端
       PCT  → /PCTxsq/ajdr/panduan 判定 → /PCTxsq/ajdr/xsqAjdr 导入
       国家 → /common/anjian/import 导入
  ④ 导入成功 → MarkHasImportCaseHandPack(caseHandId)  ← 标记已导入
```

**结论：无权限不影响你们的流程。** 下载案卷包（5.4）和导入客户端都不依赖这两个标记；它们只是界面上「已下载」「已导入」两个勾。

### 5.6 与 CPC 客户端的分工

```text
贝思兰德                          本机 CPC 客户端
────────────                      ────────────────
① StartPack 打包
② GetPackInfo 查状态
③ BatchDownloadCaseHandFile
   → OssFileUrl 下载案卷包
        │
        └────── 案卷包 zip ──────→  POST /PCTxsq/ajdr/panduan  判定
                                   POST /common/anjian/import 导入
                                   POST /sign/start/auto/sign
                                   POST /sign/auto/execute    签名
                                   GET  /commit/execute       提交官方
```

**两边的交接口就是那个 `OssFileUrl` 下载下来的 zip。**

## 十、递交实例的「其他文件」

在**某个递交实例（流程节点）**上挂附件。它与"案件文件中心"是**两条独立通道**：文件不进案件文件中心，只属于该递交实例，跟着这个节点走。

**什么时候用它**：需要随本次递交一起留档、但又不属于五书/请求书的材料（内部说明、往来函件、参考资料等）。

### 10.1 完整三步

沿用[第 5 节](#五案卷包导出交给-cpc-客户端的中间产物)的上传方式取得 `FileNo`，再关联到递交实例：

```bash
# ① 上传文件内容，取得 FileNo（与五书上传同一接口）
CONTENT_FILE_NO=$(curl -sS -k -X POST \
  "$API/NoPermissionRequired/FileStorageUploadFile?1=1" \
  -H "Authorization: $TOKEN" -H "Origin: $ORIGIN" -H "Referer: $ORIGIN/login.html" \
  -H 'Language: zh-CN' -F "file=@$LOCAL_FILE" \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["Data"]["FileNo"])')

# ② 关联到递交实例
curl -sS -k -X POST "$API/CaseInfo/UploadCaseHandOtherFile" \
  -H "Authorization: $TOKEN" -H "Origin: $ORIGIN" \
  -H 'Language: zh-CN' -H 'Content-Type: application/json' \
  -d '{
    "CaseHandId": "'"$CASE_HAND_ID"'",
    "FileTypeId": "'"$FILE_TYPE_ID"'",
    "FileRemark": "本次递交的内部说明",
    "FileGroup": [
      { "FileNo": "'"$CONTENT_FILE_NO"'", "FileTypeDescriptionId": "'"$FILE_DESC_ID"'" }
    ]
  }'

# ③ 查询该递交实例上已挂的其他文件
curl -sS -k --get "$API/CaseInfo/GetCaseHandOtherFileLists" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandId=$CASE_HAND_ID"
```

**字段对照**（界面上是"文件类型 / 文件描述 / 备注"三个下拉与输入框）：

| 界面字段 | 接口字段 | 说明 |
| --- | --- | --- |
| 文件类型 | `FileTypeId` | 外层字段，一个递交实例一个 |
| 文件描述 | `FileGroup[].FileTypeDescriptionId` | **注意：界面叫"文件描述（FileDescId）"，接口叫 `FileTypeDescriptionId`** |
| 备注 | `FileRemark` | 外层字段 |

`FileTypeId` 与 `FileTypeDescriptionId` 取自上传对话框的两个下拉（`fileTypeOptions` / `fileDescOption`），可按当前案件的 `CountryCode` / `ApplyTypeCode` / `procId` 取字典后选用（如"内部文件"）。

### 10.2 删除

```bash
curl -sS -k --get "$API/CaseInfo/DeleteCaseHandOtherFile" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseHandOtherFileListId=$CASE_HAND_OTHER_FILE_LIST_ID"
```

`caseHandOtherFileListId` 是 **`GetCaseHandOtherFileLists` 返回行里的 `CaseHandOtherFileListId`**（不是 `FileNo`、也不是 `CaseHandId`）。

修改用 `POST /CaseInfo/UpdateCaseHandOtherFileInfo`（请求体带 `CaseHandOtherFileListId`）。

### 10.3 权限：为什么这条通道能用，案件文件中心不能

**判据是递交实例的 `IsReviewing`（该账号当前能否办理这个节点）**，不是案件级的"文件中心"明细权限。

```text
案件文件中心      → 案件操作权限 的 新增/修改/删除 ×「文件中心(10)」
递交实例其他文件  → 该递交节点的 IsReviewing
```

所以：**当账号对某案件没有"文件中心"明细权限时，案件文件中心的文件删不掉，但挂到递交实例上的其他文件可以正常增删。**

> ⚠️ **服务端校验不对称（实测）**：同一容器下，`POST /CaseInfo/UploadCaseFile`（新增案件文件）**不校验**案件的"新增-文件中心"权限，而 `GET /CaseInfo/DeleteFile`（删除）**会校验**"删除-文件中心"权限并返回 `NotPermission`。
> 结果是：**能加进来，却删不掉**。若遇到这种情况，见 [13-写操作-业务码与结果契约.md](./13-写操作-业务码与结果契约.md) §7.3。
