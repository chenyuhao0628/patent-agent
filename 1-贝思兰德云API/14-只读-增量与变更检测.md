## 一、结论先说

| 问题 | 结论 |
| --- | --- |
| 有推送吗（WebSocket / SSE / 长轮询） | **没有**。前端资源里没有任何推送通道，是纯请求-响应 |
| 有站内消息中心吗 | **有接口**（`/WebSiteMessage/*`），但**本租户未启用**（`IsOpenWebSiteMessage = false`，消息数与列表均为空）。启用权在系统管理员 |
| 有"案件新动态"吗 | 有（`/NoPermissionRequired/GetCaseNewTrends*`），按类型统计受理/授权/审查意见/补正等，默认 7 天窗口。**统计的是案件动态，不包含文件上传** |
| 操作日志能当变更流吗 | `TenantOperationLog/GetQueryListCount` 实测 **403 无访问权限** |
| **那怎么检测文件更新** | **用文件中心的计数与日期筛选**，见第三节。已实测可用 |

## 三、推荐做法（三级，按需要的精度选）

### 方案 ①　只想知道"有没有变" —— 1 次请求、1 个整数

```bash
curl -sS -k -X POST "$API/CaseFile/GetFileCount" \
  -H "Authorization: $TOKEN" -H "Origin: $ORIGIN" \
  -H 'Language: zh-CN' -H 'Content-Type: application/json' \
  -d '{
    "PagedInfo": {"PageIndex": 1, "PageSize": 1, "SortField": null, "SortType": null},
    "UserTableTitleColumnList": [],
    "TableType": 20101
  }'
# => {"Data":236, ...}
```

把 `236` 记下来，下次比对：**数字没变 = 期间没有新增或删除**。只加筛选（如 `"CaseNo": "<案号>"`）即可收窄到某个案件。

### 方案 ②　想知道"新增了什么" —— 1 次请求拿增量

```bash
curl -sS -k -X POST "$API/CaseFile/GetFileList" \
  -H "Authorization: $TOKEN" -H "Origin: $ORIGIN" \
  -H 'Language: zh-CN' -H 'Content-Type: application/json' \
  -d '{
    "PagedInfo": {"PageIndex": 1, "PageSize": 50, "SortField": "UploadDate", "SortType": "descending"},
    "UserTableTitleColumnList": [],
    "TableType": 20101,
    "UploadDateStart": "<上次检查日期>",
    "UploadDateEnd": "<今天>"
  }'
```

**实测**：`UploadDateStart/End` 按**日期**过滤（传 `2026-09-01`~`2026-09-30` 得 74；传 `2026-09-14`~`2026-09-15` 得 9）。可与 `CaseNo` / `FileName` / `FileTypeIdList` 叠加收窄。

取"最新一个文件"做锚点也很省——**默认排序即上传时间倒序**，`PageSize=1` 就够：

```json
{"PagedInfo": {"PageIndex": 1, "PageSize": 1, "SortField": "UploadDate", "SortType": "descending"},
 "UserTableTitleColumnList": [], "TableType": 20101}
```

> 注意 `SortType` 只认 **`descending`**（见第四节）。

### 方案 ③　要定位到"哪个案件变了"

```bash
curl -sS -k --get "$API/CaseInfo/GetCaseFileAllListCount" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseId=$CASE_ID"
# => {"Data":1, ...}
```

对每个在办案件比对该数字。**N 个案件要 N 次请求**，比方案①②贵，但精度最高。

**建议组合**：先用方案①一次请求判断"全所有没有变"；变了再用方案②拉增量；只有需要精确到案件时才用方案③。

## 四、三个参数坑（都实测过）

| 坑 | 正确写法 | 写错的后果 |
| --- | --- | --- |
| 排序方向 | `SortType: "descending"` | 写 `desc` / `DESC` → `参数验证失败` |
| 分页对象 | 文件中心用 **`PagedInfo`**，键为 **`PageIndex` / `PageSize`**（PascalCase） | 用 `PageInfo` 或小写 `pageIndex` → `系统错误: e` |
| 日期语义 | `UploadDateStart/End` 按**日期**（含当天） | — |

其余：`TableType` 固定 **`20101`**；`UserTableTitleColumnList` 传 `[]` 即可（只要不报错，字段选择不影响计数）。

## 五、覆盖范围与局限（务必先读）

1. **只覆盖"案件文件中心"**。
   **递交实例的「其他文件」不在这套计数里**（见 [11-写操作-官方递交流程.md](./11-写操作-官方递交流程.md) 第十节），需要按 `caseHandId` 单独查 `GetCaseHandOtherFileLists`。
2. **计数范围是"账号可见的文件"**（实测 236 是全所可见量，不是个人案件量）。只要个人范围时按 `CaseNo` 循环或加其他筛选。
3. **同名文件被覆盖替换**时，数量不变 → **计数法发现不了**，需要比对 `FileNo` 集合。文件表里未见独立的"更新日期"字段；当前接口里也没有"替换文件内容"的用法（`UpdateCaseFileInfo` / `UpdateCaseHandOtherFileInfo` 改的是备注/类型这类元信息）。**若确有覆盖同名文件的场景，需另行验证。**
4. `GetCaseNewTrends*` 反映的是**案件状态动态**（受理/授权/审查意见/补正…），**不要拿它当文件变更信号**。
5. 站内消息中心（`/WebSiteMessage/*`）是唯一潜在的"推送式"信号，但需要管理员先开启；开启后可把 `GetWebSiteMessageCount` 作为最外层的一次请求。

## 六、一句话速查

```text
有没有变   → POST /CaseFile/GetFileCount                      （1 次请求，比数字）

哪个案件   → GET  /CaseInfo/GetCaseFileAllListCount?caseId=    （每案 1 次）
递交其他文件 → GET /CaseInfo/GetCaseHandOtherFileLists?caseHandId=  （单独算）
```

## 七、零额外请求的聚合信号（案件整体层面）

如果你的目的不止文件，而是"我这边的数据有没有动"，有**三个聚合接口**，各一次请求就能看出全局。

### 7.1 最省：我的案件五页签计数（1 次请求 = 5 个数字）

```bash
curl -sS -k --get "$API/CaseInfo/GetPersonalProcStatistics" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN'
```

```json
[{"Code":0,"Count":15},{"Code":200,"Count":0},{"Code":300,"Count":0},{"Code":400,"Count":9},{"Code":500,"Count":26}]
```

`Code` 就是页签状态（`0` 待办 / `200` 审核中 / `300` 待递交 / `400` 递交中 / `500` 已完成）。

**实测**：连续 3 次调用结果完全一致；且与逐页签调 `GetPersonalCaseCount` 得到的 `15 / 0 / 0 / 9 / 26` **逐一对上** → 两套口径一致，可以放心用。

> **这是检测"案件层面有没有变化"最便宜的信号**：一次请求、五个整数，任一数字变化即说明有待办/流程流转。

### 7.2 递交流程视角（1 次请求 = 9 个计数）

```bash
curl -sS -k --get "$API/CaseInfo/GetCaseHandInfoTabCount" -H "Authorization: $TOKEN" -H 'Language: zh-CN'
```

```json
{"PendingCount":4,"MyPendingCount":4,"WorkAgentCount":0,"MyWaitSendCount":0,
 "WorkAgentWaitSendCount":0,"ProcessingCount":5,"StartCount":0,"FinishCount":15,"EntrustCaseCount":0}
```

### 7.3 案件状态分布（可见范围）

```bash
curl -sS -k -X POST "$API/CaseMonitor/GetCaseMonitoringCaseStatusCountInfo" \
  -H "Authorization: $TOKEN" -H 'Origin: $ORIGIN' -H 'Language: zh-CN' \
  -H 'Content-Type: application/json' -d '{}'
```

```json
[{"StatusTypeName":"总数","Count":99,"CaseStatusTypeCode":-1},
 {"StatusTypeName":"待处理","Count":28,"CaseStatusTypeCode":1},
 {"StatusTypeName":"审查中","Count":62,"CaseStatusTypeCode":3}, ...]
```

### 7.4 建议的检查顺序

```text
第 1 层（1 次请求）  CaseInfo/GetPersonalProcStatistics   → 5 个数字，没变就不用往下走
第 2 层（1 次请求）  CaseFile/GetFileCount                 → 文件总数，没变说明没有增删
第 3 层（按需）      CaseFile/GetFileList + UploadDateStart → 只取增量
第 4 层（精确到案件）CaseInfo/GetCaseFileAllListCount?caseId=
```

| --- | --- | --- | --- |
| 案件行自带的 **`CaseProcFileTotalCount`** | 该流程的文件数 | **18/18 样本恒为 `0`**，而同一案件真实文件数是 `2` | ❌ **死字段，别用**。要文件数请用 `GetCaseFileAllListCount` |

## 十、延迟实测与同步策略

如果客户端"一个文件改动就全量拉一遍"，延迟主要来自**请求次数**，不是数据量。以下是 2026-09-14 从服务器直连 `cloudapi02` 的实测（每项取 3 次中位数）。

### 10.1 单次请求耗时与体积

| 调用 | 耗时 | 传输 |
| --- | --- | --- |
| `GetPersonalCase` [waitHand, 15 行] | ~401 ms | 159.6 KB |
| `GetPersonalCase` [delivering, 9 行] | ~436 ms | 96.5 KB |
| `GetPersonalCase` [finish, 26 行] | ~538 ms | 277.7 KB |
| `GetPersonalCase` [auditing/waitDeliver, 0 行] | ~270–291 ms | 0.1 KB |
| `GetPersonalCaseCount` | ~196 ms | 0.1 KB |
| **`GetPersonalProcStatistics`** | **~218 ms** | 0.2 KB |
| `GetCaseHandInfoTabCount` | ~352 ms | 0.2 KB |
| `CaseFile/GetFileCount` | ~270 ms | 0.1 KB |
| `GetCaseFileAllListCount` | ~217 ms | 0.1 KB |

**每个请求约 200–540 ms，且服务端耗时波动较大**（同一调用实测出现过 200 ms 与 2280 ms）。

### 10.2 串行 vs 并行（5 个页签）

| 方式 | 总耗时 |
| --- | --- |
| 串行 5 个页签 | **1954 ms** |
| 并行 5 路 | **365 ms**（≈ **5.4×** 提速） |
| 并行 3 路 | 660 ms |
| **20 路并发同一接口** | 461 ms，**20/20 全部 200** |

→ **服务端不禁并发**，并行是安全的。单次约 300 ms，总耗时基本等于 `请求数 ÷ 并发宽度 × 300ms`。

### 10.3 传输压缩：能差 49 倍

```bash
# 不带 Accept-Encoding：277.7 KB
# 带 Accept-Encoding：5.7 KB
```

响应头实测：`HTTP/2 200` + `content-encoding: br` + `vary: Accept-Encoding`——**服务端支持 Brotli/gzip**。

⚠️ **前提是客户端要发 `Accept-Encoding`**。多数 HTTP 客户端（Node 的 `fetch`、浏览器、Electron `net`）默认会发并自动解压；但**手写 socket / 部分自封装请求库不会**。上线前确认一次这一项——差 49 倍。

### 10.4 无法裁剪返回体

`UserTableTitleColumnList` **不生效**：分别传 4 个字段、空数组、不传，返回都是 **358 字段/行**、体积不变。所以**不能靠字段裁剪减小返回体**，只能靠"少发请求"。

同理，`PagedInfo.pageSize` 对耗时影响不大（实测 `pageSize=10` 反而更慢），因为服务端成本不在返回行数上。

### 10.5 推荐同步策略（按收益排序）

1. **并行化**（收益最大、改动最小）
   现在典型实现是"5 个页签依次 await"，串行 ≈ 1954 ms；改成 `Promise.all` 并行 5 路 ≈ 365 ms。

2. **加一级"变了没有"的前置判断**
   ```text
   GET /CaseInfo/GetPersonalProcStatistics   → 5 个数字（~218 ms）
   与上次比对：完全一致 → 本次同步到此结束，不发其他请求
   ```
   单文件改动若不影响案件分布，这一层就能挡住整轮全量拉取。

3. **确认 `Accept-Encoding`**（277.7 KB → 5.7 KB）

4. **分页签分级同步**
   已完成页签通常不需要每轮刷新（样本里 50 条中 26 条是已完成）。高频只看"待办 / 递交中"，已完成降频或按需。

5. **文件只做增量**
   ```text
   POST /CaseFile/GetFileCount               → 全局文件总数，没变 = 没有增删
   变了 → POST /CaseFile/GetFileList + UploadDateStart/End 只取增量
   ```
   **不要**为每个案件单独拉文件列表。

6. **缓存 + 事件驱动**
   案件列表设 TTL 缓存；只有用户点开某个案件时才拉该案件的详情、流程、文件。

7. **超时与抖动**
   服务端耗时波动大（200 ms ~ 2.3 s），需要：显式超时（建议 10–15 s）、失败重试、并发宽度限制（5–10 足够，20 路实测也没问题但没必要）。

### 10.6 改造后的量级估算

以"50 条案件、每轮同步"为例：

| 方案 | 请求数 | 估算耗时 |
| --- | --- | --- |
| 现状（5 页签 × [1 计数 + 1 列表 + 1 计数]，串行） | **15** | ~4.5 s |
| 并行 5 路 | 15 | **~0.9 s** |
| 两级检查（分布未变，直接返回） | **1** | **~0.2 s** |
| 两级检查 + 变化时并行拉 | 1 或 6 | 0.2 s / 0.4 s |

### 10.7 从"全有或全无"升级为"精确定位变化"

只有"跳过 / 全量"两档是不够的：闸门一旦击穿就要展开全部案件。加中间档才划算。

```text
① 闸门（1 次并行往返）
   Promise.all([ GetPersonalProcStatistics , CaseFile/GetFileCount ])
   → 与上次逐项比对，找出「哪些页签变了」
② 完全没变        → 结束（0 次额外请求）
③ 只有某几个页签变 → 只拉那几个页签的列表（并行）
④ 页签分布没变、但文件数变 → 只做文件增量（GetFileList + UploadDateStart），
   不展开案件同步
```

**两个容易踩的设计陷阱**：

1. **闸门里的文件计数必须限定"自己关心的范围"**。
   `CaseFile/GetFileCount` 不带筛选时是**账号可见的全部文件**（实测 236 条，是全所量级）。拿它当闸门，**同事上传任何文件都会击穿闸门**，触发本账号的全量案件同步——而自己的案件一条都没变。
   → 文件信号应只用于**触发文件增量查询**，不要用它触发全量案件同步；或先把增量文件按自己的案号过滤。

2. **"不可逆"的状态可以缓存，别只缓存终态**。
   例如结案核验：已结案的可以长期缓存，但**未结案的不该每次都查**——未结案的结案状态不会秒变。给未结案也设一个 TTL（如 15 分钟），能把每轮 N 次请求降下来。

> 判断闸门是否选对了信号，看命中率：如果"闸门未命中"里绝大多数是**文件数变化**而不是**自己的案件分布变化**，就说明第 1 条踩了。

### 10.8 并行是纯收益

实测服务端**不禁并发**（20 路并发同一接口，全部返回 200，总耗时 461 ms）。因此客户端里所有"逐案件 / 逐进程 / 逐页签"的 `for...await` 循环都应改为并发（建议宽度 5–10）。这是唯一一个"没有副作用、收益 5–10 倍"的改动，应当最先做。

## 九、关于"计数会变"的实测旁证

同一账号在 **2026-09-12** 与 **2026-09-14** 两次取到的分布：

| 日期 | 待办(0) | 审核中(200) | 待递交(300) | 递交中(400) | 已完成(500) |
| --- | --- | --- | --- | --- | --- |
| 2026-09-12 | 18 | 0 | 0 | 7 | 25 |
| 2026-09-14 | 15 | 0 | 0 | 9 | 26 |

两天内确实发生了流转（待办 −3、递交中 +2、已完成 +1），**说明计数信号是敏感的**——但也提醒：**只比对总数会漏掉"等量进出"**（例如同时新增 1 条、办结 1 条，总数不变）。要求更严时用第 3/4 层。
