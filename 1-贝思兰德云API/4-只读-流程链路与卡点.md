## 2.5 流程链路与卡点

> **前置**：需要 `$CASE_PROC_ID`，从 2.1 的列表行取得。

这一组接口回答**"案子走到哪了、卡在谁那里、卡了多久"**。

### 流程节点模型

每个案件流程都是一条**固定三节点的链**（`TotalStepNumber = 3`）：

```text
① 开始       →  ② 递交官方  →  ③ 结束
  承办人           递交人
  （撰写/准备）    （打包并递交官方）
```

节点名与办理人取自流转记录：

| 节点 | 谁在办 | 说明 |
| --- | --- | --- |
| `开始` | **承办人** | 准备申请文件、撰写答复 |
| `递交官方` | **递交人** | 打包并向官方递交 |
| `结束` | 递交人 | 流程收口 |

实测样例（同一事务所、同一流程）：

```text
开始             处理人=陈雨浩   停留=574h  ◀当前      ← 承办人还没做完
递交官方          处理人=杨佳    停留=None     待
结束             处理人=None    停留=None     待
```

```text
开始             处理人=陈雨浩   停留=0       ✓完成
递交官方          处理人=杨佳    停留=264h  ◀当前      ← 在递交人手上
结束             处理人=None    停留=None     待
```

### 流转记录

```bash
curl -sS -k --get "$API/CaseMonitor/GetProcFlowRecord" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseProcId=$CASE_PROC_ID"
```

返回该流程下的全部节点：

```json
[
  {
    "FlowStepName": "开始",
    "FlowTypeName": "递交",
    "FlowUserName": "陈雨浩",
    "StartDate": "2026-08-19T11:44:16.540623",
    "EndTDate": null,
    "StayHours": 574,
    "Sort": 1,
    "DeptFlowNodeType": 100,
    "IsFinish": false,
    "IsRunning": true,
    "IsCurrentFlowNode": true,
    "CaseHandId": "81c296c9-c9a0-4b15-add4-711ceeac7bd2"
  },
  {
    "FlowStepName": "递交官方",
    "FlowUserName": "杨佳",
    "Sort": 2,
    "IsFinish": false,
    "IsRunning": false,
    "IsCurrentFlowNode": false
  }
]
```

### 字段含义

| 字段 | 含义 |
| --- | --- |
| **`FlowStepName`** | **流程节点名**：`开始` / `递交官方` / `结束` |
| **`FlowUserName`** | **该节点的办理人** |
| `IsCurrentFlowNode` | 是否为当前节点（案子现在停在这个人手上） |
| `IsRunning` | 是否正在办理 |
| `IsFinish` | 该节点是否已完成 |
| `StayHours` | 在该节点的停留小时数 |
| `Sort` | 节点顺序（1/2/3） |
| `DeptFlowNodeType` | 节点类型，`100` = 起始节点 |
| `CaseHandId` | 递交实例 ID，仅起始节点有值 |

**回答"卡在谁那里、卡了多久"**：取 `IsCurrentFlowNode = true` 的那条，`FlowUserName` 是卡在谁手里，`StayHours` 是停留小时数。

> **适用范围**：流转记录只在**已创建递交实例**后才有。处于「待办」状态（尚未启动递交）的案件本接口返回空数组 `[]`。
>
> 待办案件要用列表行的字段判断（见下节「处理人怎么取」）。

### 全流程历史

```bash
curl -sS -k --get "$API/CaseInfo/GetCaseAllFlowHistoryInfo" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseId=$CASE_ID"
```

返回 `{CaseId, List:[{CaseProcName, ProcCreateDate, FinishDate, FlowList:[{FlowTypeName, NodeList}]}]}`，是完整的流程树。

### 递交实例与「是否已递交官方」

```bash
# 是否已创建递交实例
curl -sS -k --get "$API/CaseInfo/IsExistHandInfo" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseProcId=$CASE_PROC_ID"

# 递交实例全貌（判断是否已递交官方的主要依据）
curl -sS -k --get "$API/CaseInfo/GetHandInfo" \
  -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
  --data-urlencode "caseProcId=$CASE_PROC_ID"
```

`GetHandInfo` 返回三块：`HandInfo`（递交实例）、`CaseInfo`（案件）、`CaseProc`（流程），外加一组状态位。

#### 判断「是否已提交给官方」

| 判据 | 未递交 | 已递交 |
| --- | --- | --- |
| **`IsPackageSendSuccess`** | `false` | **`true`** |
| **「递交官方」节点的 `IsFinish`** | `false` | **`true`** |
| `CurrentFlowInfo.FlowNodeName` | `开始` 或 `递交官方` | `null`（流程已结束） |
| `ProcStatusCode` | `0`（待办）/ `400`（递交中） | **`500`**（已完成） |
| `CaseProcOperateInfo.IsExistsHand` | `false` | `true` |

**主判据用 `IsPackageSendSuccess`**，它在递交实例创建后才会出现。

实测对比：

| 页签 | 递交实例 | 当前节点 | `IsNeedSendToOfficail` | `IsPackageSendSuccess` | 节点进度 |
| --- | --- | --- | --- | --- | --- |
| 待办 | 无 | — | — | — | — |
| 递交中 | 有 | `开始` | `true` | `false` | 1/3 |
| 递交中 | 有 | `递交官方` | `true` | `false` | 2/3 |
| 已完成 | 有 | `null` | `true` | **`true`** | — |

> ⚠️ **`IsNeedSendToOfficail` 不是「还没递交」的标志**——已完成案件该字段同样为 `true`。它表示「本流程需要走官方递交」。
>
> 同理，**有些流程本来就不走官方递交**（如「请求实审」），这类案件即使标记为已完成也没有递交实例，`GetHandInfo` 返回空。

#### 状态位

| 字段 | 含义 | 实测 |
| --- | --- | --- |
| `IsPackageSendSuccess` | **打包并发送成功**（是否已递交官方） | 递交中 `false`、已完成 `true` |
| `IsNeedSendToOfficail` | 本流程是否需要向官方递交 | 递交中与已完成均为 `true` |
| `IsReviewing` | 是否审核中 | |
| `IsUndertakerId` | 是否承办人本人 | |
| `CanHurryNotice` | 是否可催办 | |
| `IsStartFlowNode` | 是否处于起始节点 | |
| `CurrentFlowInfo` | 当前节点与办理人（流程结束后为 `null`） | |
| `IsInEntrusting` | 是否委托中 | |
| `OtherFileCount` | 其它文件数 | |

`CurrentFlowInfo` 结构：

| 字段 | 含义 |
| --- | --- |
| `FlowNodeName` | **当前节点名** |
| `FlowUserName` / `FlowUserId` | **当前办理人** |
| `SerialNumber` / `TotalStepNumber` | 进度，如 `2/3` |
| `DeptFlowNodeType` | 节点类型，`100` = 起始节点 |
| `CaseHandStepId` | 节点步骤 ID |
| `IsExistsLastStep` / `IsSecondLast` | 是否有上一步 / 是否倒数第二步 |

#### 递交实例字段

| 字段 | 含义 |
| --- | --- |
| `HandInfo.CaseHandId` | **递交实例 ID**，后续表单操作用它 |
| `HandInfo.CreateDate` | 创建时间 |
| `HandInfo.CreateUserId` | 创建人 |
| `HandInfo.IsPackage` | 是否已打包（递交中 `false`、已完成 `true`） |
| `HandInfo.SendDate` | 发送日期（实测各阶段均为空，不可用作判据） |
| `HandInfo.CpcApplyType` | CPC 申请类型 |

## 2.5.1 期限字段：哪个能用，哪个不能

案件行里与期限相关的字段有三个，**含义与可靠性都不同**：

| 字段 | 名称 | 实测 |
| --- | --- | --- |
| `CaseProcLegalDate` | 法定期限 | 有值，但**未做工作日顺延**，与官方口径有偏差 |
| `CaseProcCustomDate` | 自定义期限 | 有值，比法定期限早约 30 天 |
| `CaseProcClientDate` | 客户期限 | **实测全空** |
| `CaseProcOverdueDays` / `CaseProcRemainingDays` | 逾期/剩余天数 | **实测全空**，需自行计算 |

### ⚠️ `CaseProcLegalDate` 不能当作官方期限用

**实测证据**：25 个流程里，法定期限落在周六/周日的占 **28%**（`7/25`）。若做过工作日顺延，这个比例应接近 **0%**。说明系统只做了日历运算，**没有顺延**。

对比同一案件在两个系统的期限：

| | 一种具有温控调节功能的育苗装置 |
| --- | --- |
| 通知书发文日 | 2026-06-29 |
| 贝思兰德 `CaseProcLegalDate` | **2026-08-29（周六）** |
| 官方期限（CPC 客户端 `yuqirq`） | **2026-08-31（周一）** |
| 差异 | **贝思兰德早 2 天** |

另一个案件差异更大：客户端给的是 `2026-09-28`，贝思兰德给的是 `2026-09-08`，**差 20 天**。

从流程创建日到法定期限的天数在 56～62 天之间浮动，无法用单一规则反推，**计算口径不透明**。

### 该用哪个

| 场景 | 用什么 |
| --- | --- |
| **答复审查意见 / 答复补正** 的期限 | **CPC 客户端的 `yuqirq`**（官方口径，含工作日顺延）<br>见 [CPC 分册 9-期限查询与通知书下载.md](../3-CPC电子申请客户端/9-期限查询与通知书下载.md) |
| 其它流程期限（实审请求、复审…） | 贝思兰德只有 `CaseProcLegalDate`，**偏早且不透明确**，仅供参考 |
| 剩余/逾期天数 | 两边都不给，按 `days_left()` 自算 |

> **保守用法**：贝思兰德的期限**偏早**，拿来做「提前提醒」是安全的——不会漏。
> **危险用法**：拿它判断「是否已逾期」会**误判为逾期**（真实官方期限可能还没到）。

## 2.5.2 处理人怎么取

三种角色，三个来源：

| 要取什么 | 取哪里 | 备注 |
| --- | --- | --- |
| **承办人**（撰写/准备） | 列表行 `CaseProcUndertakerUserName` | 所有页签都有值，最简单 |
| | 或流转记录中 `FlowStepName = "开始"` 的 `FlowUserName` | |
| **递交人**（递交官方） | 流转记录中 `FlowStepName = "递交官方"` 的 `FlowUserName` | |
| **当前处理人** | `GetHandInfo` → `CurrentFlowInfo.FlowUserName` | 流程结束后为 `null` |
| | 或流转记录中 `IsCurrentFlowNode = true` 的 `FlowUserName` | 待办案件无流转记录 |

**取承办人的完整例子**：

```bash
curl -sS -k -X POST "$API/CaseInfo/GetPersonalCase" \
  -H "Authorization: $TOKEN" -H 'Origin: $ORIGIN' \
  -H 'Language: zh-CN' -H 'Content-Type: application/json' \
  -d '{"PagedInfo":{"pageIndex":1,"pageSize":20},"ProcStatusTypeList":[400],
       "TableType":50013,"ActiveName":"delivering","SelectedProcIdGroup":[]}' \
| python3 -c '
import json,sys
for r in json.load(sys.stdin)["Data"]:
    print(r["CaseNo"], r["CaseProcUndertakerUserName"], r["CaseProcNameInfo"]["CaseProcName"])
'
```

列表行里与流程相关的字段：

| 字段 | 含义 |
| --- | --- |
| **`CaseProcUndertakerUserName`** | **承办人** |
| `CaseProcNameInfo.CaseProcName` | **流程节点名**（如「答复审查意见」「提出申请」「请求复审」） |
| `CaseProcNameInfo.ProcCode` | 流程代码（105 提出申请、130 答复审查意见、192 请求复审） |
| `CaseProcNameInfo.NumberResponses` | 第几次（答复类，如「一」） |
| `CaseProcOperateInfo.IsExistsHand` | 是否有递交实例 |
| `CaseProcOperateInfo.IsExistsNoFinishHand` | 是否有未完成的递交 |
| `CaseProcOperateInfo.IsCanHand` | 是否可递交 |
| `ProcStatusCode` | 流程状态：`0` 待办 / `400` 递交中 / `500` 已完成 |

> 列表行里另有 `CaseProcCurrentHandler`、`CaseProcHandUserName`、`CurrentFlowNodeName`、`CaseFlowUserName`、`LatestOfficialProcHandler` 等一批处理人字段，**实测均为空**，不要依赖。

## 2.12 案件监控维度查询

按不同维度统计与列出案件，用于**跨案件的横向观察**（谁手上积压多、哪个客户案子集中、哪个流程环节拥堵）。

```bash
curl -sS -k -X POST "$API/CaseMonitor/GetCaseMonitoringListByCase" \
  -H "Authorization: $TOKEN" -H 'Origin: $ORIGIN' \
  -H 'Language: zh-CN' -H 'Content-Type: application/json' \
  -d '{
    "HasCaseInfoMoreParam": false,
    "CaseInfoMoreParam": {},
    "StatType": 6,
    "CaseStatusCode": null,
    "ShowType": 2,
    "pageIndex": 1,
    "pageSize": 20
  }'
```

| 字段 | 说明 |
| --- | --- |
| `StatType` | **统计维度**，决定数据分组方式，见下表 |
| `CaseStatusCode` | 案件状态过滤，`null` 表示不过滤 |
| `ShowType` | 展示方式，默认 `2` |
| `HasCaseInfoMoreParam` / `CaseInfoMoreParam` | 高级筛选开关与条件对象，无筛选传 `false` / `{}` |
| `pageIndex` / `pageSize` | **平铺在顶层**，不嵌套 |

`StatType` 与接口的对应关系：

| `StatType` | 接口 | 维度 |
| --- | --- | --- |
| 1 | `GetCaseMonitoringListByClient` | 按客户 |
| 2 | `GetCaseMonitoringListByClientProject` | 按客户项目 |
| 3 | `GetCaseMonitoringListByApplicant` | 按申请人 |
| 4 | `GetCaseMonitoringListByUndertakerDept` | 按承办部门 |
| 5 | `GetCaseMonitoringListByUndertakerUser` | 按承办人 |
| 6 | `GetCaseMonitoringListByCase` | 按案件 |
| 7 | `GetCaseMonitoringListByProcess` | 按流程 |
| 8 | `GetCaseMonitoringListByOutHandler` | 按外协办理人 |

返回 `{ListData, TotalCount}`。同名查询在著作权线为 `/CrCaseMonitor/*`，参数结构一致。

### 跨案件流转观察

同一接口在监控场景下的用法：对一批案件的 `caseProcId` 逐个调 `GetProcFlowRecord`，即可得到**每个案子卡在哪个节点、卡在谁手里、多久**。

```bash
# 待办 + 递交中两类案件合并观察
curl -sS -k -X POST "$API/CaseInfo/GetPersonalCase" \
  -H "Authorization: $TOKEN" -H 'Origin: $ORIGIN' \
  -H 'Language: zh-CN' -H 'Content-Type: application/json' \
  -d '{"PagedInfo":{"pageIndex":1,"pageSize":100},"ProcStatusTypeList":[400],
       "TableType":50013,"ActiveName":"delivering","SelectedProcIdGroup":[]}' \
| python3 -c 'import json,sys; print("\n".join(r["CaseProcId"] for r in json.load(sys.stdin)["Data"]))' \
| while read -r cp; do
    curl -sS -k --get "$API/CaseMonitor/GetProcFlowRecord" \
      -H "Authorization: $TOKEN" -H 'Language: zh-CN' \
      --data-urlencode "caseProcId=$cp" \
    | python3 -c '
import json,sys
for x in json.load(sys.stdin).get("Data") or []:
    if x.get("IsCurrentFlowNode"):
        print("  卡在 %s（%s）已 %.0f 小时" % (x["FlowUserName"], x["FlowStepName"], x.get("StayHours") or 0))
'
  done
```

`GetCaseProcDetailList`（同模块）返回流程级明细，`GetCaseAllFlowHistoryInfo` 返回完整流程树。
