# 专利工作台 · 桌面开发版 0.12.8

独立桌面应用，覆盖案件管理、答复、五阶段撰写、可选的个人独立审查和贝思兰德内部流转。使用本地文件和自有界面，通过结构化接口接入 OpenCode。

## 0.12.8 标准 LaTeX 公式全链路排版与 Word 原生导出

- **全链路标准 LaTeX 公式规范**：统一在撰写技能提示词与参考文档中确立中国专利公式标准（行内公式 `$E = mc^2$`，独立编号公式 `$$\eta = \frac{P_{out}}{P_{in}} \times 100\% \tag{1}$$`），严禁使用易读性差的纯文本伪公式或 ASCII 字符拼接。
- **纯离线 KaTeX 视觉排版组件**：封装 `FormattedFormulaText` 组件，零外部 CDN 依赖、严格 XSS 防护，全面替换各页面草稿预览、最终成果预览及对比视图中的 `<pre>` 纯文本显示，支持公式自动分词、行内与块级美化排版及语法容错回退。
- **Word 原生 OMML 公式导出（DOCX）**：引入原生 MathML 与 OMML 转换引擎（`mathml2omml` 与 `katex`），在导出说明书与权利要求书 DOCX 时，将 LaTeX 公式精准转换为 Word 原生 Office Math（`<m:oMath>` / `<m:oMathPara>`）对象，无缝继承专利标准字体（宋体/Times New Roman），支持在 Word 中直接双击编辑。
- **DOCX 原件逆向解析公式保护**：升级撰写与复核技能中的 `docx_to_md.py`，内置递归 OMML 逆向解析器，提取用户交底书 Word 原件中的原生公式为标准 LaTeX 文本，彻底解决提取后符号丢失或字符坍塌问题。

## 0.12.7 案件库当前状态展示与筛选逻辑修复

- **案件生命周期状态清晰分类**：确立 7 大标准业务状态（待处理、办理中、流转中、等待官方、已授权、已驳回、已结案），与列表【当前状态】列深度对齐，支持本地与远程同步案件。
- **工具栏升级为真正的【当前状态】筛选器**：移除原先仅局限草稿步骤的“办理状态”筛选，替换为直观的【当前状态】下拉框，动态提取当前案件池存在的状态，支持一键筛选出“只看待处理”、“只看在办”、“只看已驳回”等。
- **底层业务终态与催办判定修复**：修正 `isFinishedOrWaitingBusiness`，将已授权、已驳回与已结案案件正式移出在办及期限催办范围；点击顶部【在办】卡片时精准排除已出结论与已办结的历史案件。
- **当前状态列自然序排序优化**：点击【当前状态】表头排序时优先按业务生命周期序（待处理 -> 办理中 -> 流转中 -> 等待官方 -> 已授权 -> 已驳回 -> 已结案）排列，改善原拼音打散问题。

## 0.12.6 内部转交回读空 GUID 匹配修复与案头统一总刷新

- **转交回读匹配误报修复**：修复贝思兰德接口在转交成功后返回的下一个流程节点中 `FlowUserId` 经常为全零 GUID（`00000000-0000-0000-0000-000000000000`）导致 `matchesNextFlow` 误判为不匹配、触发“已发送内部转交请求，但下一节点回读未匹配；请刷新核对，不要重复转交”误报的问题；当其为全零 GUID 时安全回退按真实办理人姓名（`FlowUserName`）校验，显式不同用户 ID 仍严格拦截；转交提交后增加 300ms 延迟缓冲，避免数据库读写分离延迟。
- **转交宿主刷新自愈（TransferHost.refresh）升级**：支持在 `uncertain` 状态下通过 `matchesNextFlow` 比对远端流转，一旦确认已在目标责任人名下立即自动升级自愈为 `submitted` 并落盘，彻底消除中断或时序导致的流程死锁。
- **前台隐藏零散局部刷新按钮**：移除内部转交弹窗内的「刷新回读」、流程记录卡片中的「刷新流程」、案件信息卡片中的「刷新备注」以及案件空间顶部的「重新判读」等零散按钮，精简前台操作干扰，底层保持后台拉取与联动能力完整。
- **案头统一总刷新架构**：在案件空间顶部操作栏提供唯一的**【刷新本案】**总入口，点击一次即可并发刷新本案流程记录、写回全局流程缓存、重新判读官方结论、刷新案件元数据，并通过 `refreshSeq` 静默联动前台内部转交等模块；配合全局案件库顶部的「刷新案件」（全库轮询与增量同步），形成“全局刷新 vs 本案刷新”清晰双层刷新体系。

## 0.12.5 内部递交云端已保存识别、空草稿穿透与刷新自愈

- **拓宽答复材料与通知契约校验**：修复 `isRemoteTransferSaved` 答复路线文件名仅支持“意见陈述”的正则缺陷，支持匹配包含“答复”、“审查意见”或任意 `.docx` 的真实上传文件；通知书发文日、名称与发文序号在 `OpinionStatement` 为空时自动回退读取关联通知信息（`GetCaseHandProcRelateNoticeInfo`）。
- **本地陈旧空草稿穿透与远端反推**：修复本地 `04_内部说明/` 下存在历史 0 文件的空草稿（`phase === 'draft', files: []`）时在 `inspect()` 与 `prepare()` 中劫持会话、导致界面锁死在“核对并保存材料”的问题；自动穿透空草稿并根据远端实际状态重水化为 `saved`。
- **刷新操作全链路自愈升级**：修复 `refresh()` 在草稿态（`draft`）时未校验 `isRemoteTransferSaved` 导致永远无法自愈回读的缺陷；刷新确认远端文件与表单就绪后立即自动升级为 `saved` 并实时落盘。
- **保存校验放行远端已有材料**：修复 `validateReview` 答复路线在远端已有 Word 文件时因本地未重复选文件误拦截报错的缺陷。

## 0.12.4 内部递交重开防误触、撤销保存与状态自愈

- **重开异步回读防误触与加载保护**：修复应用重开或重新进入递交页面时，在后台异步回读（`inspect`）远端状态期间因无 loading 状态导致用户误点「使用工作台稿件」触发全新草稿覆盖已存会话的时序问题；增加全局 `inspecting` 加载遮罩与状态保护。
- **保存时间戳实时更新与远端流程懒加载**：`save()` 成功时实时刷新 `s.view.at` 时间戳，保证本地磁盘会话具备最高排序优先级；修复重开后未调 `prepare()` 时缺少 `s.remote` 导致保存报错的缺陷，按需自动懒加载远端流转信息。
- **全链路「撤销保存 / 重新编辑」与状态回退**：新增核心 `TransferHost.revoke(key, id)`，贯通 IPC 与 Preload，支持将已保存（`saved`）或不确定（`uncertain`）状态安全撤销回草稿态，完整保留已填表单、补正条目、文件副本与已选接收人。
- **已保存状态全局横幅与直达提交 / 撤销**：已保存状态重新打开应用或进入递交页面时，直达「下一办理人与结果」或在起草/表单页顶部清晰展示「材料与表单已在贝思兰德云端保存就绪」横幅，提供直接转交或撤销保存通道，不再回退显示“确认保存本次递交材料”。

## 0.12.3 内部递交跨端接力、自动重授权与状态自愈

- **跨设备云端递交接力**：在一台电脑上保存了递交材料与表单后，即使未在本机发起转交，在第二台已登录的电脑上打开该案，系统通过只读契约（`isRemoteTransferSaved`）自动识别云端已就绪材料，自动反推为 `saved` 状态并直达「下一办理人与结果」页；第二台设备无需本地文件副本即可自由更换接收人并执行内部转交。
- **本地会话与状态持久保留**：递交材料和表单保存后，关闭重开或重新进入提交页面，直接读取服务端已有文件与表单状态，避免重复递交；已有草稿在重新读取时受到保护，不被远端空记录覆盖。
- **保存密码自动重授权**：修复 `verifyLogin(force=false)` 在登录过期时因过早退出导致无法使用 Keychain 已保存凭据自动重授权的缺陷，实现后台与重检时自动静默刷新 Token。
- **递交流程异常死锁自愈**：修复保存或启动递交实例被网络中断后，因 `submissionAttempted === false` 导致 `refresh()` 无法自愈而永久卡在 `uncertain` 状态的缺陷；点击刷新时根据远端实际状态精准恢复。
- **转交前置远端契约强校验**：在 `SubmitHandFlow` 执行前，强制校验远端五书/答复文件与表单完整性，防止因网页端删改文件而提交残缺实例。
- **交互体验与缓存优化**：已转交（`submitted`）案件重新打开时正确定位至结果页（Tab 2）；仅在起草阶段显示来源提示；移除转交点击瞬间对前端缓存的过早清除，避免接口报错时丢失用户输入。

## 0.12.1 案件状态与接口降载解耦

- 侧栏「业务工作」分组新增「案件状态」；内部流转页每案同步显示结论徽标并可按结论筛选；每个案件的概览「案件信息」显示「案件状态」与「流程状态」，案件标题栏也带结论徽标（所有页签可见），并可按案「重新判读」。除新增这两处显示外，导航、路由与其他页面结构不变。
- 结论只有三种：**已授权**（办理登记手续通知书 `200602` 或专利证书 `40000x`）、**已驳回**（驳回决定 `200305`/`210407`/`210408`）、**未见结果**；从未查询过的案件显示"未判读"，本机案件显示"—"。同时出现授权与驳回时按最新发文日 `postDate` 判定（复审撤销驳回后授权判定为已授权）；日期相同或缺失时依 0001 §3.7 规范优先判定办登/证书。
- 判读只用案件官文清单 `CaseInfo/GetNoticeListByCaseId`（请求体带 `PagedInfo`，最多翻 5 页，命中结论即停）。**不下载、不导入、不写回贝思兰德**，也不读案卷的 `AuthorizeDate`/`CertificateNo` 等字段（实测可能长期为空）。
- 常规同步中不发起官文清单查询，未选总工作文件夹时立即前置拦截；`RemoteFlow` 增加前端轻量缓存，切换 Tab 保持流转图，杜绝重复发接口。（判读触发方式在 0.12.2 按用户确认改回跟随同步，见下节；其余降载与缓存保留。）
- 「未见结果」只说明官文清单里没有授权/驳回类官文，**不等于官方未授权**（官文清单不是完整历史，实测抽查 12 案有 7 案清单为空）；清单翻页到上限仍无结论时额外标记"结果待复核"。
- 判读失败只记录在同步提示里，保留上一次结论，不写入新结论，也不影响聚合门控快照；账号切换后结论随账号隔离。
- 官方结论随案件共享索引 `案件信息.json` 写入，另一台电脑读回目录时可见。

## 0.12.2 官方结论接入案件状态

- 授权/驳回结论出来后，案件**不再显示"等待官方处理结果"，也不再留在「等待官方」列表**：当前办理节点直接显示「已授权」或「已驳回」，案件回到案件库，侧栏与卡片计数同步减少；内部流转、概览「流程状态」行同样显示结论。
- 贝思兰德流程页保留真实的递交与回执字段，并新增一行「官方结论：已授权/已驳回（官文名 日期）」说明所内流程不会自动推进。
- 判读跟随正常同步：未出结论的案件每轮同步判读（含聚合门控命中——授权/驳回通知不一定新建流程，统计不变也可能刚出结果）；已出结论的 7 天内不重复判读；「重新判读全部案件」与案件内「重新判读」仍可强制刷新。**该触发方式与 0.12.1「只在手动点击时判读」相反，按用户 2026-09-15 的确认改为跟随同步。**
- 只有授权/驳回才算"结果已到"。「未见结果」仍然是等待官方：官文清单不是完整历史（实测抽查 12 案有 7 案清单为空），不能据缺失推断未授权。
- 已归档与已结案的案件不再自动判读；不自动归档，也不生成办登或复审待办（用户只需要知道授权/驳回结论）。
- 不改写贝思兰德数据：递交状态、回执、流程节点全部保持原样，官文结论只在本机分层显示。

## 安装与更新

- macOS Apple Silicon：以 `release/release-manifest.json` 中的 0.12.8 `.pkg` 和 `.app` 为准。
- Windows x64：以 `release/release-manifest.json` 中的 0.12.8 NSIS `.exe` 为准。

安装器沿用固定应用标识，覆盖程序并保留用户数据。Mac 安装到所选安装域的“Applications”目录；安装前的系统目录旧版本不在此断言，以 `release/release-manifest.json` 与实际 Info.plist 为准。Windows 使用 NSIS 安装器，保留安装路径与 AppData。旧便携版应退出后使用安装器，原便携 EXE 不属于安装器管理的文件。

账号、加密凭证和本机设置放在应用数据目录，原始申请库与工作目录独立选择。Mac 安装与重复覆盖曾经实测，但最新安装实证停在 0.3.0（`evidence/workbench-v030-acceptance.json`，2026-09-13），0.9.x–0.12.x 的安装验收需重新记录；Windows 已交叉构建和检查安装器内容，尚未实机验收。当前包未做发行签名 / macOS 公证，也没有在线自动更新服务。版本与 SHA-256 以 `release/release-manifest.json` 为准。

## 0.5.0 对话操作与本地进度

- 正式答复默认“办理当前步骤”；分析中断后继续分析，完成后明确选定策略，选定后进入起草。可以主动切换“仅讨论”。长回复在对话区内部滚动，输入框与状态保持可见。
- 左侧“内部流转”展示本机打开案件、确认材料、意见分析、选定策略、稿件、复核与定稿；撰写按实际阶段确认显示。贝思兰德节点和转交分别留在案件的流程和提交页。
- 运行状态显示当前动作、耗时和最近活动；执行记录及供应商返回的思考内容可展开。供应商未返回时明确显示暂无，不混入正式回复或后续模型上下文。
- 停止或退出后保留已输出文字、思考和任务记录；重开由用户选择继续或重试。继续利用当前上下文，重试在新分支重新执行本轮。
- 可编辑历史用户消息、重新生成回复并切换旧分支；运行中重发先等待停止，旧任务迟到输出不进入新任务。切换分支不回滚案件文件及业务状态。
- 恢复期间用本机执行记录阻止重复命令、下载及安装；结果未明时要求先核对。自定义 MCP 不在恢复请求中自动重放，需要核对后用新的明确消息触发。已有成果按当前文件和版本重新核对，不恢复模型内部推理位置。

## 版本规则

使用“主版本.功能版本.修复版本”：重大产品版本或不兼容变化增加第一位；新增功能增加第二位，并将第三位归零；兼容的小修复增加第三位。主版本增加时，后两位归零。仅更新文档不自动升级安装版本。

当前开发版为 **0.12.8**：在 0.12.7 之上，实现全链路标准 LaTeX 公式规范、纯离线 KaTeX 视觉排版组件、Word 原生 OMML 公式导出（DOCX）及 DOCX 原件逆向解析公式保护。仍处于开发阶段，版本增加不代表未验收能力已完成，历史证据不改号。

## 0.9.7 同步与慢任务修复

- 下载阶段只保存副本，不发布旧案件索引。最终合并保留同步期间较新的流程、官方状态、权限和手动材料；同账号写入串行提交，账号/目录变化拒绝迟到结果。
- “刷新案件”执行全量读取，绕过结案与附件列表缓存，并强制重查未取得回执的递交状态；不会重新下载已就绪文件。已经取得回执的终态流程不受强制刷新击穿，只按更长的六十分钟缓存复用，避免重复查询不会变化的递交结果。正在增量同步时的全量请求合并为一次后续全量，不重复并发。
- 自动同步每三十秒检查是否距上次结束已满五分钟；失败也保留自动重试冷却，手动刷新不受此限制。当前流程及未就绪材料仍查询。历史流程文件列表缓存三十分钟，已结案件状态缓存十五分钟；未结案件状态最多复用三分钟，因自动同步间隔为五分钟，实际每轮重查。递交状态缓存未出回执五分钟、已出回执六十分钟；缓存各最多 2000 项，过期/账号切换失效。结案状态可重新核验，不假定永远不变。缓存时长属于可调整的工程参数。
- 对话准备阶段显示实际的排队、材料准备、办理权限核验及后台启动。诊断记录各阶段耗时、同步触发来源与脱敏批次/案件/流程关联、首个转发响应数据块，并每三十秒采样主进程事件循环延迟和内存。首个数据块不等于首个正文 token。
- 冻结材料及启动副本采用有界读取；子进程日志跨输出分片脱敏，过长单行直接省略。LibreOffice 相关命令使用每次调用的独立 HOME/XDG 环境，不再删除另一命令的配置；真实各平台转换效果仍需独立验证，优先使用内置阅读转换。
- 指定 0.9.3 日志实际为 315 次请求、314 次响应，响应耗时合计 55.316 秒，且无模型或超时事件；此前“接口占满十分钟、已确定拖慢模型”的归因不成立。本次完善诊断，不声称已解决尚未复现的真实慢任务。

## 撰写参考材料

1. 打开当前处于撰写阶段的案件，在“撰写 → 本案参考材料”点击“添加参考材料”。
2. 从本机多选技术交底、图纸或参考专利：支持 DOCX、DOC、PDF、TXT、Markdown、PNG、JPEG，每次 1–12 份，每份不超过 20MB。
3. 文件复制到本案的 `01_通知与材料/撰写参考/`，原件保留，同名文件分别保存。新添加文件自动勾选，可以取消不需要的材料；退出或离开页面后再进入，需要重新选择本次材料；只有本次勾选内容进入撰写任务的冻结副本。
4. “打开查看”使用本机默认应用打开本案副本；“移出列表”只取消手动参考材料的列表关联，保留磁盘副本和历史任务输入，不影响其他案件。同步通知和原始申请不能在此移除。
5. 添加成功表示文件已保存，不表示解析成功。点击生成后，在本阶段任务／工具记录查看读取结果与失败原因；旧 DOC、扫描文件等仍受转换器和模型能力约束。没有文件时可以直接输入文字构思。

任务运行、阶段不可编辑或案件同步过程中不允许改动参考材料；取消系统选文件对话框不会添加材料。文件导入是本机复制，不会向贝思兰德上传。开始模型任务后，所选内容按当前模型配置供 AI 读取。

- 每案只有一个当前办理，按真实流程节点显示。官方回执进入“等待官方处理结果”，不等于案件结案；等待官方使用独立侧栏。
- 案件库支持公司名称、点击表头排序、拖动列宽、专利类型和办理业务组合筛选、批量归档。申请、审查意见和补正分色显示；勾选框与筛选字号已统一。

## 工具权限与体积

设置 → 文档工具提供联网检索、软件下载、任意命令与软件安装、预设转换组件自动安装四个选项。新增下载与命令默认关闭；设置本机共用，运行中需先停止任务再修改。

- 开启任意命令后，Agent 可执行 shell / PowerShell、调用已有 WPS / Word / 系统工具、安装任意轻量库或其他软件。没有 Office 白名单。命令以本机当前用户权限运行，可访问其他文件和联网，默认目录不是沙箱；命令联网不受独立检索 / 下载开关限制。
- `discover_tools` 返回实际检测到的工具及默认位置；WPS 安装检测不代表已验证该版本的自动转换接口。先探测再调用，不猜测其命令行参数。
- `prepare_material` 仅复制本次选定材料；Agent 用 `execute_command` 另存转换 / OCR 结果，再用 `read_work_file` 阅读或视觉核对。来源材料 ID、实际读取摘要和命令记录保留。应用不主动向命令环境传递凭证或整个案件库，但开放任意命令不是操作系统隔离。
- `download_file` 支持任意公开软件 URL，下载到集中目录；逐跳检查地址，限制 2 GiB，支持预期 SHA-256 校验，不自动运行。没有预期摘要时仅报告实际摘要，不冒称可信验证。命令可用包管理器自行下载与安装。
- `web_search` / `web_fetch` 通过 Exa 查询公开网页，保留来源；不携带账号凭证，不把外部资料作为操作指令。
- Mac 原有系统 `textutil` 可读普通旧 DOC，无需下载。LibreOffice 固定版本安装仍是可选快捷方式；完整引擎不放进主包。扫描 PDF 已提供页图和模型视觉。

工具根目录是 Mac `~/Library/Application Support/专利工作台/tools/` 或 Windows `%APPDATA%\专利工作台\tools\`。`downloads` 保存下载文件和来源记录；`custom` 默认保存自装工具、Python 虚拟环境、npm 依赖和缓存，应用覆盖更新时保留。本次命令 HOME / 临时文件和材料副本留在各任务自己的 `command-work`，不进入共享原始库。Agent 若指定系统安装位置，则由相应安装器管理。

命令、退出码、限长输出保存在各本机任务的 `tool-audit/*.json`，界面保留调用记录。停止会终止所管理的命令进程；已经独立启动的 GUI 应用或系统服务不保证随任务关闭。主程序仍只捆绑 OpenCode 和文档阅读组件，不要求安装旧项目源码。

适配 DeepSeek Responses 的 reasoning_text/content 事件到当前 OpenCode SDK 可读取的思考事件，工具续轮将对应内容还原为 DeepSeek 请求格式；仅作用于 DeepSeek Responses，不更改供应商、密钥或用户选择的协议。界面显示“思考内容”，缺失时说明尚未接收到，不能推定模型没有返回。

日志按自身记录时间轮换，不再依赖 Windows 可能保留的文件创建时间；补记模型名称、实际上游 HTTP 状态及原始错误的安全类型/状态码。传输仍有上限：图文请求及本机会话响应各 16 MiB，模型响应流 64 MiB，诊断磁盘总量仍为 5 MiB。超限、响应格式不兼容及流中断分别提示。

## 0.8.2 保存工具即时校验与模型修复

write_artifact 保存 JSON 时即时校验语法，并在答复任务中核验当前任务字段、选定策略和复核版本；错误作为工具反馈返回模型，模型可在同次运行中修正后再次保存，无须重读全部材料。工具支持 content 直接传对象，由程序序列化，减少长正文的双层转义问题。未通过的最近候选保存在本次隔离输出目录的 result.json.rejected.json，不覆盖之前有效文件，也不允许用旧产物冒充本次修正成功。最后主机仍执行独立校验；模型忽略错误或运行被停止时不伪报完成。不改变思考等级、模型输出上限或协议设置。

运行器同时检查结束条件：模型自然结束但没有合格产物时，在同一后台会话自动发回具体问题继续修复，最多追加两次完成检查修复，不重新创建业务任务、不重读全部材料；仍受原任务停止信号与运行时限约束。连续修复仍失败才暂停并保留内容，不把“模型说完成”当作交付完成。


## 0.9.0 分项保存与完成检查闭环

正式任务支持 write_artifact 的 mode=merge：按顶层字段逐项保存，未提供的字段保留；数组及嵌套对象整体替换。inspect_artifact 返回已存字段、待办和指定字段内容。分项检查点不等于完成产物；字段、实际材料读取和业务完成条件全部通过后才交付。恢复仅接受相同案件阶段、任务类型、策略、材料内容和冻结稿件的检查点；材料快照临时编号更新不会导致已有内容丢失。

保存工具预演与主机最终接收相同的业务转换，缺少读取、重复编号等可修复问题返回模型继续处理，不直接采用稿件或推进阶段。完成检查的自动续办以进展判定：连续两次无新保存内容或读取结果才暂停，有进展继续；原运行时限和停止信号保持不变。未修改模型、协议、思考等级或输出限制。

界面在合格稿件下明确提示“查看与比较 → 采用 → 独立复核 → 定稿”。这些用户决定不由模型自动代办。研究依据：[工具反馈循环](https://www.anthropic.com/engineering/building-effective-agents)、[长任务增量进展](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)；采用其中适合本项目的工具与检查点设计，不照搬固定轮数或多代理结构。

界面入口：设置 → 诊断日志导出最近十分钟记录；本案对话顶部五节点可点击进入办理步骤；工作任务按开始时间由新到旧排列。


## 0.9.1 可选复核、报告布局与稿件自动带入

修改前申请文件仅供比对、不上传；本次修改后的申请文件仅在有修改时提供，保存时提取勾选部分；意见陈述书是答复正文。不能从“建议修改文字”猜测完整申请稿，缺少完整修改内容时显示具体补齐提示。长篇独立审查报告使用独立滚动容器，避免覆盖下方工具记录。

## 0.9.4 LibreOffice 启动崩溃修复与任务时限放宽

以下为历史记录；0.9.7 改为独立命令环境，不再清理共享 profile。

- 修复 soffice 命令行启动崩溃：模型用 execute_command 手动跑 soffice 时，soffice 复用默认 profile；该 profile 若上次被强杀会残留 `OfficeRestartInProgress` 标志，配置层 `ReadWriteAccess::create` 失败导致 `std::__terminate` → abort（SIGABRT）。现在 execute_command 检测到 soffice/libreoffice 调用时，先清理默认 profile 目录，让 soffice 用全新干净 profile 启动。应用内置的 read_material 转换路径本就用独立 profile，不受影响。
- 加强系统提示：旧 DOC 转换优先 read_material；明确不要用 execute_command 直接跑 soffice/libreoffice，改用 WPS/pandoc/antiword 等非 LibreOffice 工具。
- 后台任务运行时限由 10 分钟（600_000ms）放宽至 60 分钟（3_600_000ms），减少长任务（含多材料读取、组件首次准备）撞时限。MCP 连接超时仍为 10 分钟，与任务时限无关。
- 验证：tsc 通过；400/400 自动化通过（新增 LibreOffice profile 清理回归）。历史 0.2.8 的"任务上限 10 分钟"记录保留为历史事实。Windows 真机与真实案件仍待验收。

## 0.9.5 贝思兰德同步优化：跳过已就绪流程的文件列表查询

以下历史分析中的同步耗时归因和全量刷新声称，经复审核验不成立；以 0.9.7 纠正与有限缓存方案为准。

- 诊断日志（10 分钟窗口）显示同步阶段对每个案的每个流程都调 `GetCaseProcFileList`（125 次）+ `GetUpdateCaseInfo`（101 次），其中大部分是已就绪流程的无效查询，拖慢同步、占用主进程异步 IO，让人误以为"案件分析很久"。
- 优化 `desktop/service.ts` sync 主循环：非当前办理流程、且该流程已有材料全部就绪时，本轮跳过 `client.files(p.id)`（GetCaseProcFileList）查询。当前办理流程必查（最可能有新文件）；首次同步（无 round 或材料未就绪）也会查；手动刷新或退出重登可重新拉取全量。
- 预期：40 案多流程的 GetCaseProcFileList 调用从约 125 次降至 40-50 次（只查当前流程 + 未就绪流程），同步耗时显著下降。模型不接触贝思兰德接口（架构不变），看图保持可选。
- 验证：tsc 通过；400/400 自动化通过（含现有 sync 集成测试，证明不破坏基本同步/下载/重试流程）。Windows 真机与真实案件仍待验收。

## 0.9.6 贝思兰德同步优化：已结案件结案状态跨轮缓存

以下五分钟缓存为历史策略，已由 0.9.7 的可强制失效、十五分钟缓存替代；不再假定结案不可撤销。

- 诊断日志分析：GetUpdateCaseInfo 共 101 次，98% 间隔 ≤1s，是 2-3 轮 sync × ~40 案 caseClosure 串行批量调用（每案每轮查一次结案状态），非同案重复。
- 优化 `desktop/service.ts` sync：已结案件（`closure.finished=true`）5 分钟内复用上次 caseClosure 结果，跳过 GetUpdateCaseInfo 查询；未结案件每轮查（及时检测结案）。结案后不会撤销，缓存安全；登出/切换账号清空缓存。
- 预期：已结案件（约 12 案）在第 2-3 轮 sync 不再查 GetUpdateCaseInfo，101 次 → 约 77-89 次。配合 0.9.5 的 files 跳过，同步总耗时进一步下降。

## 0.11.0 贝思兰德聚合变化检测
