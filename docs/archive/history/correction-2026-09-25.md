## 1. 本轮目标

围绕“更快、更可靠地检查材料和提交状态”修正工作台，而不是单纯增加功能或装饰界面。

本轮需要同时解决两类问题：

- 预览、材料、表单、流程状态之间的信息是否足够支持人工核对；
- 页面是否把同一信息重复展示、把不同重要程度的信息放在同一层级，造成界面冗杂和判断负担。

产品边界保持不变：案件管理、答复、撰写、独立审查和贝思兰德内部流转都属于产品范围；本轮重点是答复和内部流转的检查体验，不把产品收缩成单一递交工具。

## 3. 当前问题记录

### 3.1 预览与检查

- 提交预览已经可以显示 DOCX 正文、图片和公式，但解析逻辑集中在一个较大的文件解析函数中。
- DOCX 预览目前主要覆盖段落、分节标题和嵌入图片；表格、Word 原生公式、复杂版式和解析诊断还没有统一模型。
- 预览结果通过文本、Data URL 和可选分件数组传递，后续材料变大时可能增加 IPC 和内存压力。
- 图片、正文、表单、五书差异和接收人虽然都能检查，但页面仍然把很多内容放在同一页，检查路径不够明确。

### 3.2 转交和提交

- `TransferHost` 同时负责会话、文件、副本、远端读取、保存、撤销、回读和状态恢复，新增路线时修改面会继续扩大。
- 路线、文件角色、五书编码和表单字段固定在类型与常量中，增加复审、无效或其他机构适配时需要修改多处。
- 界面仍按姓名匹配当前需求规定的默认办理人，与已经存在的办理人偏好和候选列表机制不完全统一；姓名应集中为可替换的产品默认配置，而不应散落在组件中。
- `uncertain`、`submissionAttempted`、`submissionRetryable` 等状态通过多个字段组合表达，状态边界继续扩大后容易出现非法组合。

### 3.3 全局 UI

- 当前页面同时承担“当前状态说明、材料选择、差异比较、表单编辑、远端清单、接收人选择、操作日志和风险确认”多种任务。
- 页面上有多层按钮、说明文字和重复状态信息；用户需要自行判断哪些是必须核对、哪些只是辅助信息。
- 需要从信息层级、分组、渐进披露、保存反馈和响应式布局重新整理，而不是只做颜色和间距调整。

## 4. 修正顺序

4. 形成“必须看到 / 展开才看 / 进入详情才看”的信息分层表。

### 阶段 B：低风险检查体验修正

1. 统一提交核对页面的信息层级：案件与流程摘要、材料核对、表单核对、接收人和最终操作。
2. 将辅助说明、历史日志和差异正文改为可展开区域。
3. 统一保存、回读、待核验、已转交和失败反馈的位置和文案。
4. 已完成：业务专属案件页隐藏重复的“办理业务”筛选。
5. 已完成第一步：保留需求规定的“杨佳”默认办理人行为，并将默认值集中到 `DEFAULT_INTERNAL_TRANSFER_RECIPIENT`；下一步再接入账号或机构偏好，多候选时仍要求明确选择。
6. 为预览增加“来源、版本、文件哈希、分件范围、解析警告”摘要。

### 阶段 C：预览内核

1. 把 DOCX、图片、纯文本和后续 PDF 解析统一为文档 AST。
2. 每个节点保留来源文件、页/分件、段落位置和解析警告。
3. 增加表格、Word 原生公式和复杂文档的可解释降级显示。
4. 对图片和大文本采用受控缓存、缩略图和按需加载。
5. 预览失败时显示“哪一份材料、哪一部分、为什么需要人工核对”，不能只返回空正文。

### 阶段 D：转交架构

1. 用路线注册表描述申请、答复、补正等业务的文件角色、表单、校验和远端接口。
2. 把 `TransferHost` 拆为状态机、持久化、文件准备和平台适配器。
3. 为保存、撤销、刷新、内部转交建立显式合法状态转移表。
4. 为本地记录增加 schema migration，保留旧版本可读性。
5. 将贝思兰德接口的只读、幂等和可重授权属性从接口命名正则改成显式元数据。

### 阶段 E：产品化验证

1. 用合成案件验证正常、空状态、部分材料、解析警告、网络失败、保存中断和跨设备回读。
2. 桌面端验证至少包含宽窗口、窄窗口、长正文、长文件名和大量材料。
3. 每次 UI 修改同时验证首屏、主要动作、错误反馈、键盘操作和滚动位置。
4. 真实账号写操作仍需单独授权；本轮只验证界面和隔离的合成服务端行为。

## 5. 设计原则与历史证据

- 采用 Material 3 的 list-detail 和 supporting-pane 思路：主内容承担主要检查任务，辅助信息放入支撑面板，而不是所有内容平铺在同一层级。
- 采用 Fluent 2 的 reflow、show/hide 和 re-architect 方法：窗口变窄时重排和收起次要信息，不能只是把桌面布局压缩。
- 采用 Primer 的保存反馈原则：保存模式保持一致，失败时保留用户输入，结果在当前上下文中明确反馈；破坏性操作提供可理解的确认和恢复路径。
- 采用渐进披露：首屏只呈现当前判断所需的信息，证据、历史、技术细节和完整正文按需展开。
