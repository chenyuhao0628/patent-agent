# 程序阶段与修改依据控制

## 一、先确定程序阶段

在评价补充、删改或“原文是否支持”之前，先标记：

- `pre-filing`：尚未提交，交底书、图纸、实验记录和申请人确认可作为起草输入；
- `post-filing`：已经提交，只能以原始提交文件及依法可用材料判断修改基础；
- `unknown`：程序阶段不明，不对可否补入作确定结论。

本技能不处理审查意见答复，但对任何已提交申请的修改审查均须执行本门禁。程序阶段不明且拟修改可能增加技术内容时，停止修改并列为待确认事项。

## 二、区分来源角色

逐份文件标记：

- `current-draft`：当前待审申请稿；
- `original-filed`：原始提交文本及附图；
- `invention-disclosure`：发明交底或研发说明；
- `drawing-source`：结构图、流程图、照片或CAD导出；
- `test-record`：真实实验、检测或计算记录；
- `internal-review`：问题清单、批注、修改说明；
- `prior-version`：旧稿或历史修改稿；
- `external-reference`：现有技术、标准或第三方资料。

当前稿用于确定审查对象，不当然证明新增内容具有修改基础。内部审核意见、工程常识和外部资料不得替代原始公开。

## 三、使用等级

对拟采用的每项事实标记：

1. `express`：文字或附图明确记载；
2. `directly-derivable`：由同一来源直接、唯一地得出；
3. `reasoned-inference`：需要机理或工程推理，必须列为待确认；
4. `engineering-completion`：原材料没有公开，仅因工程上通常需要而补全，禁止直接写入正式文本。

不得把“可能存在”“通常需要”或“为了可实施应当设置”写成原文件已经公开的确定事实。

## 四、冲突处理

- 当前申请稿与交底书冲突时，不自动以交底书覆盖当前稿；
- 申请稿与图纸冲突时，记录冲突对象、位置和可能影响；
- 多个旧稿冲突时，只以用户指定的正式版本为审查基线；
- `post-filing`阶段不得用未随申请提交的交底书补救原始公开缺陷；
- `pre-filing`阶段可以结合交底材料完善申请稿，但技术事实、关系和参数仍须获得申请人确认。

使用`assets/source-admissibility-template.csv`记录来源、阶段、使用等级和冲突状态。
